## 9. Critical issue 1: label-source confounding

### 9.1 Why it exists

The authenticity label is entangled with the image-production pipeline:

- generated = GPT-Image-2 synthetic pipeline;
- real = six separate public source datasets.

The local handoffs reportedly found major source differences, including:

- generated files apparently all PNG;
- most real files JPEG;
- metadata present in many real files but absent in generated files;
- alpha-channel differences;
- a fixed generated resolution pattern for UI screenshots.

Removing metadata prevents direct metadata leakage but does not remove historical compression, resampling, source style, typography, rendering, resolution, or acquisition differences.

### 9.2 Why a random split does not solve it

Random train/validation/test splitting distributes the same production pipelines across all splits. A high test score can therefore reflect accurate recognition of familiar source pipelines rather than robust authenticity detection.

Per-category reporting is useful but does not eliminate the confound because, within a category, the real and generated samples can still come from different production processes.

### 9.3 Minimum required mitigations

Recommended experiments include:

1. **Uniform re-encoding robustness:** decode and re-encode all images using the same format and quality setting, then evaluate performance change.
2. **Metadata-free loading:** continue using decoded pixels only.
3. **Resolution/aspect-ratio shortcut baseline:** measure how well simple non-semantic source statistics predict the label.
4. **Simple color/compression baselines:** evaluate whether trivial global statistics already separate the labels.
5. **Leave-one-category-out evaluation:** train on five categories and test on the held-out category. This is imperfect because category and source are linked, but it is more informative than random within-source splitting.
6. **External or independently aligned validation:** use another legal and suitable dataset if possible, or reserve an independently sourced/generated confirmatory set.
7. **Narrow claims:** explicitly say “on TextRich” and “for GPT-Image-2 samples” where appropriate.

The current 2,400-image experiment is best treated as a pilot unless a stronger confirmatory design is added.

## 10. Critical issue 2: “layout” is not isolated from density and OCR quality

OCR boxes encode more than arrangement. They reflect:

- number of text regions;
- amount of text-covered area;
- character size;
- contrast and legibility;
- font/rendering properties;
- resolution;
- OCR detection failures;
- malformed or duplicated generated text.

B1 includes direct density-related features such as region count and coverage. B2 occupancy maps also encode total occupied area. Therefore, if B1, B2, or fusion outperforms the visual baseline, the improvement cannot automatically be attributed to spatial arrangement.

### 10.1 Controls that should become mandatory

1. **Density-only baseline**
   - Example inputs: `num_regions` and `text_coverage_ratio` only.
   - Purpose: determine how much performance comes from the amount of detected text.

2. **Arrangement-focused baseline**
   - Use normalized or selected features that minimize direct count/coverage information.
   - Purpose: test relative positioning or dispersion beyond raw density.

3. **Shuffled-layout fusion control**
   - Keep the same visual-layout fusion architecture, but assign each image a layout representation from another sample.
   - Ideally shuffle within category and density band so obvious distribution changes do not make the control trivial.
   - Purpose: separate meaningful image-layout alignment from extra capacity or generic layout-distribution effects.

4. **Matched-density comparison**
   - Compare real and generated samples with similar density within the same category.
   - Purpose: reduce the possibility that density alone explains authenticity classification.

5. **Blank/random layout control, if resources permit**
   - Keep branch architecture and parameters but feed a constant or random map.
   - Purpose: test whether the additional branch itself acts as regularization.

Without these controls, the safest wording is “OCR-derived region representation,” not “spatial layout caused the gain.”

## 11. Critical issue 3: extra model capacity

The fusion model has a layout branch and fusion layers that the visual-only baseline does not have. If fusion wins, the result may be due to:

- genuinely useful layout information;
- extra learnable parameters;
- regularization effects;
- training instability or hyperparameter differences.

Layout-only B1/B2 models do not fully resolve this. A shuffled-layout fusion or parameter-matched control is needed. The exact C-model variants must also be declared before test evaluation:

- visual + B1 only;
- visual + B2 only;
- visual + B1 + B2;
- or a clearly limited set of predeclared variants.

Do not select the “best” C variant using the test set.

## 12. Critical issue 4: density analysis is category-confounded

The q33/q67 thresholds were correctly computed from training data only, which helps prevent test leakage. The problem is that global density tertiles may largely encode content category:

- tables are naturally dense;
- posters and charts have distinct layout distributions;
- UI screenshots can be sparse or structured differently.

Therefore, a performance decline in the high-density bin may mean poor table performance rather than a general density effect.

Recommended analyses:

1. report category × density × class cell counts;
2. compute density bands within category, or use continuous density;
3. run stratified or regression-style analysis controlling for category and authenticity;
4. report per-category density slopes or trends;
5. avoid causal wording such as “density causes failure” unless the design truly identifies a causal effect.

The current density metric, polygon-union area divided by image area, is a reasonable operationalization but differs from TextFake’s recognized-character-count proxy. This distinction should be stated.

## 13. Critical issue 5: sample size and statistical uncertainty

The current test set has 360 images, or approximately 60 per category. Splitting further by authenticity and three density bands can produce cells with roughly ten or fewer observations.

Risks include:

- unstable subgroup F1/recall;
- wide confidence intervals;
- undefined or misleading AUROC for small or single-class cells;
- exaggerated percentage changes caused by one or two samples.

Three random seeds measure training stochasticity, not sampling uncertainty.

Recommended improvements:

- predeclare one primary metric, likely AUROC or balanced accuracy depending adviser preference;
- choose classification thresholds using validation data only;
- report secondary accuracy, precision, recall, and F1;
- calculate paired bootstrap confidence intervals for A-versus-C differences on the same test samples;
- report confidence intervals for subgroup results;
- label small-cell subgroup findings exploratory;
- use a larger untouched confirmatory test set if computationally and procedurally possible;
- provide a learning curve or computational justification for using only 2,400 of over 12,000 available images.

The prior GO/MODIFY/DROP thresholds of roughly +3 or +5 percentage points are engineering heuristics, not automatically scientific thresholds. Base conclusions on uncertainty, consistency, practical effect, and resource cost.

## 14. Critical issue 6: the “lightweight” claim

MobileNetV3-Small is a lightweight visual backbone. The end-to-end proposed detector also requires OCR and layout processing. The handoff reports approximately 2.095 seconds per image for OCR on CPU.

To retain “lightweight” in the title or contribution, evaluate:

- end-to-end latency;
- OCR latency separately;
- classifier latency separately;
- total model/storage size;
- peak memory;
- throughput;
- hardware specification;
- possibly energy or CPU-only practicality if claimed.

Otherwise, narrow the phrase to “lightweight visual backbone” or remove “lightweight” from the title.

## 19. Recommended revised experimental matrix

The exact final design must be agreed with the adviser and constrained by available compute. A scientifically stronger matrix would be:

### 19.1 Core models

- **A — Visual baseline:** MobileNetV3-Small using pixels only.
- **D — Density-only baseline:** minimal region-count and coverage features.
- **B1 — Full layout statistics:** the planned 16-feature classifier.
- **B1-A — Arrangement-focused statistics:** selected/normalized layout features that reduce direct density information.
- **B2 — Layout-map model:** the planned 64 × 64 occupancy-map classifier.
- **C1 — Visual + B1 fusion:** if this is the primary fusion representation.
- **C2 — Visual + B2 fusion:** if resources allow a second predeclared fusion representation.
- **C-shuffled — Shuffled-layout fusion:** same fusion architecture with mismatched layouts, preferably shuffled within category/density strata.
- **C-blank/random — Capacity control:** optional if shuffled control is insufficient or adviser requests it.

Do not create so many variants that the thesis becomes unmanageable. If compute is limited, prioritize A, D, B1 or B2, one primary C, and C-shuffled.

### 19.2 Primary research contrast

The strongest primary question is not merely whether C beats A. It is:

> Does correctly aligned OCR-derived spatial information improve detection beyond visual information, density, and comparable extra model capacity?

The most informative contrasts are:

- C versus A;
- C versus D and layout-only baselines;
- C versus C-shuffled;
- performance under uniform re-encoding;
- performance across category-controlled density levels.

### 19.3 Recommended claim hierarchy

- If C does not beat A: layout representation provided no reliable added value under the tested conditions.
- If C beats A but not C-shuffled: improvement may reflect capacity or layout-distribution effects, not aligned spatial information.
- If C beats A and C-shuffled but not D: density may explain most of the gain.
- If C beats A, D, and C-shuffled consistently: stronger evidence that aligned spatial information adds value.
- If improvements disappear after re-encoding or external testing: gains may depend on source/compression shortcuts.
- If improvements persist across these controls: a much stronger and more defensible contribution.

### 30.4 Other closest works and their consequences

#### A. TIQA / ANTIQA Appendix B.2 — text-specific fusion already exists

Source: <https://arxiv.org/html/2603.07119v2>

TIQA is primarily a perceptual text-quality assessment paper, but Appendix B.2 is crucial. It decomposes images into text crops, extracts a 192-dimensional ANTIQA descriptor from every crop, mean-pools crop features, concatenates them with a global DRCT image embedding, and trains an MLP for real-versus-generated classification. On its combined evaluation, the paper reports ROC-AUC increasing from 0.967 for standalone DRCT to 0.973 for DRCT plus ANTIQA features over three seeds.

Difference from the proposed thesis:

- ANTIQA captures crop-level glyph/text-rendering appearance and perceptual quality.
- It does not represent page-level arrangements of OCR boxes.
- It does not ask whether layout adds value beyond density.
- It does not use a shuffled-layout or capacity-matched auxiliary control.

Consequence: never claim “first text-aware fusion for AI-generated image detection.” The novelty must distinguish **text appearance** from **page geometry**.

#### B. TextFake — OCR text-density analysis already exists

Source: <https://arxiv.org/html/2606.01050v1>

TextFake is a 20,000-image multilingual text-rich AIGI benchmark. Its “Text Density Curse” analysis runs OCR and uses recognized character count as a density proxy, comparing low, mid, and high percentile bins. It reports that many spatial/frequency detectors degrade strongly with increasing text density.

Difference from the proposed thesis:

- OCR is used for measurement/annotation, not as a trainable page-layout branch.
- It does not isolate bounding-box arrangement from density using aligned-versus-shuffled geometry.
- It is a benchmark/diagnostic study, not the same TextRich fusion experiment.

Consequence: density must be a control or interaction variable, not a standalone novelty claim. The proposal should cite TextFake and explain why character count/occupied area is insufficient to establish spatial layout value.

#### C. PatchHead — spatial AIGI detection and a shuffle control already exist

Source: <https://arxiv.org/html/2608.09223v1>

PatchHead is a generalizable AIGI detector that preserves the two-dimensional organization of DINO patch tokens and applies a lightweight spatial aggregation head. It also shuffles patch positions as an ablation and observes a performance decrease, using that result to analyze the value of native spatial arrangement.

Difference from the proposed thesis:

- Its spatial evidence comes from visual foundation-model patch tokens, not OCR bounding boxes.
- It is not focused on text-rich images or TextRich.
- It does not isolate text density or OCR detectability.

Consequence: do not claim “first spatial AI-image detector” or “first position-shuffling control.” Claim the narrower OCR-page-layout/text-rich application and use PatchHead to justify why shuffling is a legitimate control.

#### D. TextRich — same dataset, but the requested method remains open

Source: <https://arxiv.org/html/2606.19259v2>

TextRich contains 12,095 images in six categories and evaluates five existing AIGI detectors plus a VLM in a zero-shot setting. Its paper explicitly concludes that text- and layout-aware detection methods are needed.

Difference from the proposed thesis:

- TextRich does not train an OCR-derived layout detector.
- It does not isolate density, arrangement, capacity, or OCR detectability.

Consequence: TextRich supplies the benchmark and explicitly motivates the gap, but it supplies no dataset novelty. It does not need to be replaced solely because of novelty concerns.

#### E. OCR Graph Features for Manipulation Detection — OCR geometry in forensics is old prior art

Source: <https://arxiv.org/html/2009.05158v2>

This work uses OCR character boxes and graph features such as height, width, alignment, relative y displacement, and distance, then trains a Random Forest to detect manipulated characters in business documents.

Difference:

- Localized manipulation rather than whole-image fully generated authenticity.
- No multi-domain TextRich benchmark.
- No visual-plus-page-layout fusion.

Consequence: never claim that OCR geometry is new in digital forensics.

#### F. Text-line Examination for Document Forgery Detection — layout alignment for authenticity dates back at least to 2013

Source: <https://doi.org/10.1007/s10032-011-0181-5>

This paper automates forgery detection using text-line rotation and alignment. It demonstrates that document layout/geometry has long been used as an authenticity clue.

Difference:

- Traditional document-line tampering, not fully generated images.
- No learned visual-layout fusion, density control, or TextRich evaluation.

Consequence: acknowledge the historical forensics lineage rather than presenting alignment/spacing as newly discovered.

#### G. ADCD-Net — OCR masks already appear inside document forgery networks

Source: <https://arxiv.org/html/2507.16397v1>

ADCD-Net is an ICCV 2025 document forgery localization model. It fuses RGB and DCT evidence and uses a CRAFT OCR-derived text/background mask as a prior for estimating pristine background features.

Difference:

- OCR identifies text versus background; it does not model the relational/global arrangement of boxes.
- The task is local tamper localization, not classifying a fully generated page.

Consequence: occupancy masks and OCR mask integration are not individually novel. The thesis must prove that **arrangement**, rather than mere occupancy/text-region detection, adds value.

#### H. DocCogito — an OCR-box grid layout target already exists outside forensics

Source: <https://arxiv.org/html/2603.07494v1>

DocCogito projects OCR text-line bounding boxes onto the spatial patch grid of a vision encoder and uses the resulting grid-level supervision map to pretrain a lightweight layout tower.

Difference:

- Document question answering/reasoning, not authenticity.
- Layout is a supervision target for visual tokens rather than a standalone forensic input branch.

Consequence: a 64 × 64 or similar bounding-box layout map is not novel as a representation by itself. The contribution is the forensic research question and control structure.

#### I. SynJAC — rendering OCR layout into an image already exists outside forensics

Source: <https://arxiv.org/html/2410.01609v2>

SynJAC proposes Layout-to-Vector, which transforms OCR/PDF bounding boxes into a color-coded layout image and uses CNN/RoIAlign features in a multimodal document-understanding model.

Difference:

- Key-information extraction/domain adaptation rather than authenticity detection.
- Uses semantic entities and a larger multimodal framework.

Consequence: do not claim invention of “turn OCR layout into an image and process it with a CNN.”

#### J. FLiD — lightweight MobileNet text/document forgery detection already exists

Source: <https://arxiv.org/html/2605.09089v2>

FLiD uses YOLO11 to localize face and text fields, a frozen MobileNetV3-Small to extract embeddings, a compact 191k-parameter classification head, and score fusion for identity-document forgery.

Difference:

- Localized ID-field forgery rather than fully generated multi-domain pages.
- YOLO field localization rather than OCR page geometry.

Consequence: MobileNetV3-Small, text-region focus, fusion, and “lightweight” are not novelty claims. End-to-end OCR plus inference cost must be measured if lightweight remains in the title or contribution.

### 30.6 Required controls are now part of the novelty, not optional polish

Because prior work occupies the individual ingredients, the strongest contribution is the experimental isolation. The following branches/comparisons should be treated as core:

1. **Visual-only baseline.** Same visual backbone and training budget.
2. **Density-only branch.** At minimum OCR box count, total box area/occupied fraction, or another explicit density proxy.
3. **Aligned true-layout branch.** Uses the actual OCR spatial arrangement.
4. **Shuffled-layout branch.** Preserves count, box sizes, and preferably marginal x/y/area properties while destroying their correct page arrangement.
5. **Capacity-matched auxiliary control.** Random/noise or permuted auxiliary input with the same dimensionality and fusion head so improvement cannot be attributed only to more parameters.
6. **Category-conditional reporting.** Prevent density bins from simply becoming category proxies.
7. **Density-conditional reporting.** Ask whether layout helps within comparable density levels.
8. **Multiple seeds and uncertainty.** Report variation and confidence intervals, not a single lucky run.
9. **Source/format robustness where feasible.** At least test compression/format perturbation or clearly limit the claim.
10. **Optional external validation.** TextFake is the preferred adjacent benchmark if scope and licensing permit. This would strengthen generalization, but it is not mandatory for the core TextRich novelty question.

## 42. Density concept: current understanding and unfinished lesson

The student requested that density be taught slowly before model capacity.

### 42.1 Concepts already explained

Text density was defined as how much text is detected in an image and how much image area it occupies. Two simple indicators discussed were:

- number of OCR-detected regions; and
- text-coverage ratio.

The reported density definition is:

> polygon-union area of OCR-detected regions divided by source-image area, multiplied by 100 for a percentage.

Example used:

- a 1,000 × 1,000 image has 1,000,000 total pixels;
- if the unique OCR-region union covers 200,000 pixels, density is 20%.

The student asked how the program detects overlapping OCR polygons. It was explained that OCR polygons contain corner coordinates in a common image coordinate system. A geometry union operation or equivalent binary mask counts overlapping pixels once rather than summing them twice.

Evidence-status warning was preserved: polygon-union density is reported in the prior handoff, but the exact implementation, geometry library, and correctness remain unverified until the actual code is inspected.

### 42.2 Density-only model clarified
